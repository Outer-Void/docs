Engineering and governance reference, kept current by the documentation-synchronization pass that follows
every stage. Full reconciliation **2026-10-26** after Stage 23; incremental syncs after Stages 24–26 and the JADIS Toolbox checkpoint (2026-10-26).

> Standalone where it makes sense. BLUX-integrated everywhere it adds genuine value. Contract-driven.
> Auditable. Replaceable. No duplicated authority.

## Authority boundaries

| Component | Owns | Never owns |
|---|---|---|
| **BLUX** (`blux`) | Contract v1, the capability registry and policy, Model API v1 and provider/model routing, Hook System v1, the runtime that orchestrates intelligence operations, and the direct `blux` CLI | Device control (VoidForge), receipt persistence (BLUX System), audits (DAT), discovery (GOD), repository creation (LRC), product business truth (each product) |
| **`blux`** | Direct intelligence: `blux "explain this error"`, `cat build.log \| blux "diagnose"`, `git diff \| blux "review"`, `blux chat`, `blux --model blux-code "..."`, plus `blux agent` and Contract v1 machine commands | Being the universal ecosystem, project or device CLI |
| **AXIOM / `ax`** | The developer control plane. It routes each command to the authoritative engine and exits 69 when that engine is missing. AXIOM is also the identity of the `axiom` cockpit environment | Reimplementing any engine |
| **CogA** (blux-coga) | Deterministic structured reasoning with replayable artifacts | Model identity; hidden chain-of-thought (never stored) |
| **cA** (blux-ca) | Construction, modification and repair changesets with rollback | Certifying its own work (results say `certified: false`; DAT validates) |
| **DAT** (dat) | Independent audit, security, quality and release gates. It may reject any component's work | Fixing what it finds |
| **LRC** (lrc) | Deterministic repository creation, scaffolding and migration | Certifying itself |
| **GOD** (god) | Discovery of capabilities, projects and commands | Execution of anything it discovers |
| **BLUX System** (blux-system) | Intelligence-free execution truth: receipts, operation graph, provenance, replay metadata, artifact references | Reasoning, planning, orchestration |
| **BLUX App** (blux-app) | Read-only observability viewer | Execution or enforcement |
| **BluxGPT** (blux-gpt) | Provider transport behind Model API v1: retries, streaming, normalization | Agent loops, tool execution, routing across providers, ecosystem authority |
| **blux10k** | Environment and toolchain authority (`ax env`) and dotfiles | Project or device work |
| **JADIS Toolbox** (`jadis`, jadis.toolbox) | *This workstation*: environment classification, doctor, safe journaled local repairs and bootstraps, reproducibility snapshots | Dotfile management (blux10k), routing (`ax`), audits (DAT), discovery (GOD), devices (VoidForge), intelligence (BLUX: read-only access only) |
| **VoidForge** | Android device work: ADB, Fastboot/fastbootd, sideload, flashing, Magisk, its journal and local authorization | Being directed by BLUX: BLUX and `ax devices` can only ask, and writes need the person at the VoidForge device |
| **AXIOM Launcher** (void.os) | Launcher behavior, launcher state, the bundled VOID.SYS and AXIOM Shooter surfaces | Requiring BLUX |
| **Products** (Roughin, Vigyl, Resolver) | Their own business, financial, care and moderation truth | Delegating that truth to BLUX (BLUX may only assist, where integrated) |

The detailed contracts live in the BLUX repository: [Contract v1](https://github.com/Outer-Void/blux/tree/main/contracts/v1),
[Model API v1](https://github.com/Outer-Void/blux/tree/main/docs/model-api),
[Hook System v1](https://github.com/Outer-Void/blux/tree/main/docs/hooks), and the
[capability contract ADR](https://github.com/Outer-Void/blux/blob/main/docs/adr/0003-capability-contract.md).
A repository integrates by declaring capabilities in a `.blux/` directory (present today in blux, blux-coga,
blux-ca, dat, lrc and god). A missing `.blux/` is valid wherever BLUX integration is
intentionally excluded.

## When to use `blux` and when to use `ax`

- **`blux`**: ask a model something. Use it to explain, diagnose, review or chat. It is also how you run
  BLUX's agent loop or Contract v1 machine commands.
- **`ax`**: get developer work done through the right engine:
  - environment: `ax env`;
  - reasoning: `ax reason`;
  - build or repair: `ax build`;
  - repository creation: `ax create`;
  - audit: `ax audit`;
  - discovery: `ax projects`, `ax capabilities`, `ax tools`;
  - execution truth: `ax inspect`;
  - devices: `ax devices`.

  `ax ask` and `ax agent` forward to `blux`. Check `ax routes` and `ax doctor` for what resolves on a
  machine.

## BLHermes

BLHermes (`Outer-Void/blhermes-agent`) was an Outer Void fork of Nous Research's MIT-licensed `hermes-agent`.
BLUX replaced it:
- the forensic inventory, parity matrix and characterization goldens are in
  [blux `migration/blhermes/`](https://github.com/Outer-Void/blux/tree/main/migration/blhermes);
- the decoupling proof is in
  [docs/migration/blhermes-deletion-readiness.md](https://github.com/Outer-Void/blux/blob/main/docs/migration/blhermes-deletion-readiness.md).

After the Stage 17 manual review the owner chose **archival**. The repository is read-only on GitHub at final
commit `dc8abc1db0`, with its MIT licence and Nous Research attribution intact (credits `LIN-001`).

The parity matrix tracks 44 BLHermes features. Their migration states are:

| State | Features |
|---|---|
| MIGRATED | 8 |
| IN_PROGRESS | 10 |
| NOT_STARTED | 15 |
| DEFERRED | 5 |
| CHARACTERIZED | 2 |
| PLANNED_REMOVAL | 3 |
| KEPT_AS_ATTRIBUTION | 1 |

Where a capability is not started or deferred, the archived fork remains reference material only. BLUX code is
clean-room; no BLHermes code was copied without provenance accounting.

## Evidence model

These words are not synonyms. Every status claim names its level:

| Term | Meaning |
|---|---|
| implemented | Code exists |
| tested | Automated tests exercise it (unit or mock) |
| integration-tested | Tested across real component boundaries (processes, sockets, files) |
| real-provider-tested | Run against a real external model provider |
| hardware-tested | Run on physical devices, with recorded reports |
| release-qualified | Passed the product's release gate, with recorded evidence |

Test counts are always quoted with the commit and date they belong to. Prefer the reproducible command to the
number.

### Status vocabulary

The required values are:

| Status | Meaning |
|---|---|
| NOT_STARTED | |
| PLANNED | |
| IMPLEMENTED | |
| MOCK_TESTED | |
| INTEGRATION_TESTED | |
| HARDWARE_PENDING | Implemented, but the hardware evidence it needs does not exist yet |
| BLOCKED | A named blocker prevents progress |
| RELEASE_CANDIDATE | |
| RELEASED | |
| ARCHIVED | |

Additions:

| Status | Meaning |
|---|---|
| NOT_APPLICABLE | The dimension does not apply |
| NOT_RELEASED | No release has been made, and none is claimed |
| UNVERIFIED | Not checked in the evidence window; nothing is claimed |
| OPTIONAL | Integration exists or is allowed, and is never required |
| EXCLUDED | Integration is deliberately absent |
| REQUIRED | The component needs it to function |

## Training and datasets

`blux-ca-dataset` and `blux-coga-dataset` are deterministic, generated evaluation and training datasets for cA
and CogA (Hugging Face card layout, BLUX Proprietary License). BLUX's `training/` directory is reserved; no
training pipeline exists.

Rules:
- Provider hidden chain-of-thought is never stored.
- Private user or project data is never added to datasets automatically.
